Distributed Emergency Resource Matching

People hit by a disaster ask for water, food, medicine, transport or shelter. Volunteers and NGOs register what they can give. The system matches each request to the nearest resource with enough left, and keeps working when a storage node dies.

How a request flows

The client only ever talks to one gateway. Everything after step 2 happens asynchronously.

ClientPOST /requests with type, location and quantity
Request servicestores it, replies 201, publishes to RabbitMQ
RabbitMQpriority queue: urgent requests go first
Matching servicefinds the nearest resource with enough quantity
Reserve + assigna saga: if assigning fails, the reservation is undone
Storagecoordinator routes to 1 of 3 shards, each with a replica

What makes it robust

Sharded and replicatedKeys are hashed into 12 partitions spread over 3 shards. Every write goes to a primary and its replica before it is confirmed.
Survives node failureIf a primary dies, the coordinator promotes the replica and retries. Clients see no error. The node resyncs when it returns.
Never over-allocatesEvery record has a version. Two matchers racing for the last units cannot both win: one write is refused and retried.
Real distanceMatching uses great-circle distance between coordinates, within 50 km, and skips resources that have too little left.
Backs off under stressWhen storage is briefly unavailable, callers wait longer between retries (with jitter) instead of piling on.
Runs on KubernetesStatefulSets for storage, Deployments for services, an Ingress gateway. Pods that die are replaced; matching scales out.
